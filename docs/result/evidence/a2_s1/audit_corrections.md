# A2.S1 evidence audit — 2026-09-03

This audit supersedes interpretations in commit `a63a5ef`, while retaining the original request outputs and timings. It does not modify the canonical prompts or keyword scorer.

1. **Direct runtime backend:** `CPuFriend/bin/llama-server.exe --list-devices` returns `(none)`. The directory contains CPU backends and no Vulkan backend. The original command passed `-ngl 32` but did not assert a GPU device. Treat the successful direct measurements as CPU observations, not as successful Vulkan partial offload. There was no captured full device trace for those original runs, so the retrospective identification also assumes that the installation did not change between the runs and this audit.
2. **No ubatch causal proof:** switching from Ollama to CPuFriend also changed build and available backends. Success cannot be attributed to `-ub 16` alone.
3. **Device discovery versus inference:** the installed Ollama server can discover Arc 140V when `GGML_BACKEND_PATH` points to its own `vulkan/ggml-vulkan.dll`. This read-only check does not qualify Qwen3 inference. Do not load this DLL into the different CPuFriend build.
4. **Cache mismatch:** the old Ollama benchmark warmed up and repeated an identical prompt without forcing cache eviction. The direct benchmark explicitly used `cache_prompt=false` and returned `cache_n=0`. The old raw Ollama evidence omits cached-token counts. Consequently, neither a 176x/697x TTFT regression nor a full-prefill throughput advantage is established. CPU versus Vulkan, different builds and single samples versus medians also confound comparison.
5. **Deadline enforcement:** the 4K direct request completed at 349.820 s with first token at 333.053 s. It crossed the predeclared 300 s TTFT limit. The original harness did not cancel that request at the threshold. Larger direct contexts were not attempted afterwards. Label this a completed observation that violated the gate, not a successfully enforced early stop.
6. **Quality cap:** the first saved candidate run used 96 tokens; the subsequent 128-token run is authoritative for the canonical comparison. Preserve both. Non-streaming quality did not measure TTFT; prompt-eval duration must not be relabeled TTFT.
7. **Control repair:** A2.1 used Ollama/f16/16K; the candidate's working method used CPuFriend/q4 KV/4K/CPU. The audit runs all 20 affected 14B cases using the latter method, sequentially with no Qwen3 model loaded. It also reruns the three predeclared 96-token challenges. Original HTTP 500 challenge attempts remain in evidence and are not counted as model-quality failures.
8. **Manual review:** the earlier 2.65 candidate average was too generous to incomplete outputs (notably B03, C03 and C04), and D03's request for an absent diff should not be called a hallucination or refusal. The audit applies the user's same 0–3 rubric consistently to both candidate and control outputs; the historical review remains a separate snapshot.
9. **Metadata:** head dimension is 128 from explicit attention key/value metadata, not `2048/32=64`. Shared expert FFN length is zero and the actual tensor inventory contains no shared expert tensors. Structural active footprint can be derived from tensor shapes; it is not a measured FLOP count.
10. **Resource evidence:** low available memory was observed, but the old runs did not collect a Qwen3 peak-commit trace, GPU shared-memory trace or sustained pagefile I/O trace. Counters collected during the control audit belong to 14B and cannot fill those missing Qwen3 measurements. Window responsiveness was not directly tested.

The hardware qualification cannot be promoted on the old GPU/performance claims. Dense 32B remains blocked and Track B implementation stays unchanged.
